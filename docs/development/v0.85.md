## Bluetooth Stage 1～3

Stage 1 introduced Classic RFCOMM SPP on the CYW43439 with device name `CPB-PicoCalc`. Stage 2 added a separately switchable Bluetooth Console and shared ANSI/runtime input path. Stage 3 added binary-safe SPP transport for XMODEM／YMODEM and a File Transfer route selector.

RX ownership is exclusive among Console, Test Terminal, and Transfer. Bluetooth Console ON is not required for File Transfer; Bluetooth must be ON and SPP connected.

## Route resolution

The File Transfer selector provides AUTO, USB CDC, UART0, and Bluetooth SPP.

1. explicit route from the menu
2. AUTO + command source: USB／UART／Bluetooth keeps that source
3. AUTO + local PicoCalc input: connected USB CDC, otherwise UART0

An explicit route never silently falls back. Bluetooth connection alone does not capture a locally started AUTO transfer.

## Final Bluetooth/YMODEM architecture

- Bluetooth RX ring: **8192 bytes**
- Bluetooth TX ring: **2048 bytes**
- transfer prefetch: **2048 bytes**
- bulk, binary-safe RX
- immediate RX overflow detection
- bounded drain for short protocol-control TX
- post-transfer 350 ms quiet-window RX quarantine
- duplicate Block 0 ACK + `C` recovery
- pre-data timeout ACK + `C` recovery
- partial packet timeout: NAK／retry
- YMODEM receive: single-file and multi-file batch
- YMODEM send: single-file
- final empty Block 0 ACK
- Block 0 size-based exact commit

A completed earlier file remains committed if a later batch item fails. The current incomplete file is aborted transactionally.

## Firmware update UX

Control Center adds:

- Firmware → Enter BOOTSEL
- Firmware → Reboot

The USB composite device adds Raspberry Pi's reset vendor interface beside CDC and MSC. `flash-cpb.cmd` uses `picotool -f` and defaults to `CPokecombasic.uf2`. Hardware verification passed for Enter BOOTSEL, Reboot, and the script. An older firmware needs one physical BOOTSEL installation before this interface exists.

## Audio／display follow-up

- VM cooperative BREAK polling services background work during RUN
- six DMA buffers provide about 139 ms audio headroom
- PAINT services audio every eight flood-fill seeds
- LIST's one-row scroll prerenders the footer before changing scroll origin
- WAV ending ramps roughly the final 5 ms and avoids enqueueing an empty tail buffer
- BREAK stops program and audio; END／STOP and ordinary runtime error leave background audio running

## Key Click

Control Center → Audio → Key Click cycles OFF, SOFT, CLASSIC, SHARP. CLASSIC is the default and the value is stored as `key_click=...` in `RMBASIC.CFG`.

Only a physical PicoCalc key accepted by the REPL／Control Center path clicks. RUN input through INKEY／PAUSE／BREAK and USB／Bluetooth remote input do not. Click PCM mixes with ongoing PLAY／WAV.

## SD long-line architecture

| backend | lines | body characters |
|---|---:|---:|
| RAM | 256 | 191 |
| SD | 1,024 | 2,047 |

AUTO inherits its selected backend's limits. Body length excludes the line number and separating space. Exact boundaries are accepted; one-character overflow is rejected without truncation.

The SD index records line number, file offset, full-line hash, and body length. A reusable 2,080-byte scratch buffer belongs to the SD backend. LOAD／LIST／RUN／SAVE, dirty-session restore, compiler input beyond character 191, and USB MSC return/index rebuild were covered by regression tests. SD→RAM conversion rejects a long line with `LINE TOO LONG FOR RAM` and preserves the source.

PicoCalc interactive program entry and Direct mode remain 191 characters. Long source lines are intended for files brought in from a PC or another transfer path.

## Storage continuity

`RMBASIC.SES` describes the verified editing session; transactional source files and `RMBASIC.BAK` support recovery. The startup notice appears only when a dirty session was recovered. Fresh UNTITLED and clean named sessions remain silent.
