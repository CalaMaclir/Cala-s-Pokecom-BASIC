# Version 0.90 Stage 4 test1 — PSRAM Editor History

## Scope

Stage 3 passed its target hardware gate with Build #490. PicoCalc's 8 MiB
PSRAM passed detection, Quick 1 MiB, Full 8 MiB, and three full stress passes
with matching CRC32 and zero errors. Stage 4 uses that optional memory only for
volatile full-screen editor history. ProgramStore remains the source of truth;
the current edit line, VM, audio, keyboard, wireless, and storage state remain
in internal SRAM.

## Undo and redo

- F4: Undo.
- F9: Redo.
- Printable insertion, Backspace, Delete, Insert Line, and Delete Line are
  reversible.
- Adjacent repeated operations of the same kind are coalesced. Cursor movement
  and editor commands end the group.
- A new edit after Undo clears the Redo stack.
- Save records a revision checkpoint, so Undo/Redo can return to or leave the
  saved state with the dirty marker updated correctly.
- History is editor-session-only and is released when the editor closes.

The history uses two CRC-protected fixed-record circular stacks in a 128 KiB
PSRAM claim. This provides approximately 31 coalesced Undo steps and 31 Redo
steps while leaving almost all of the 8 MiB device available for later stages. Each record stores one complete logical-line snapshot, cursor,
line index, existence state, and revision. The oldest snapshot is evicted when
a stack is full. A deleted 2,047-character line can therefore be restored
without copying the complete BASIC program.

If PSRAM is unavailable, corrupt, or reports an I/O failure, editing continues
through ProgramStore and only Undo/Redo is disabled. The message is either
`UNDO REQUIRES PICOCALC PSRAM` or `UNDO DISABLED: PSRAM ERROR`.

## PicoCalc function-key layout

PicoCalc labels the shifted function-key layer as F6 through F10. The
editor UI and documentation therefore use the PicoCalc key names rather than
`Shift+F1` through `Shift+F5`:

| Key | Action | Key | Action |
|---|---|---|---|
| F1 | Save | F6 | Save As |
| F2 | Find | F7 | Goto Line |
| F3 | Next Match | F8 | Previous Match |
| F4 | Undo | F9 | Redo |
| F5 | Insert Line | F10 | Delete Line |

F1 automatically opens Save As when the program is untitled. Escape exits the
editor and retains the existing unsaved-changes confirmation. For external
keyboards, both direct F6-F10 codes and F1-F5 plus a held Shift modifier are
normalized to the same command layer.

## PSRAM ownership

The driver exposes a single-client claim for `EditorHistory` and
`Diagnostic`. The editor requests 128 KiB and leaves the remaining carrier
capacity unallocated. A destructive diagnostic is rejected with
`PSRAM IN USE` while another client owns memory. The reversible 16-byte boot
probe tail is excluded from client allocations.

## Cursor path

Navigation no longer redraws the old and new source rows. Stage 3 removed row
highlighting, so those LCD writes were redundant. Left/Right now update only
the changing location row and hardware cursor. Up/Down also update the lower
line/wrap indicator; a full redraw occurs only when the viewport actually
changes. Cursor movement never reads or writes editor history PSRAM.

## Host validation

- Existing editor model suite.
- Coalesced character Undo/Redo.
- Backspace Undo and saved-revision recovery.
- Redo invalidation after a new edit.
- Insert Line and Delete Line restoration.
- PSRAM-unavailable fallback.
- Fixed-record PSRAM stack read/write, counts, release, and CRC corruption.
- Editor sources compile with `-Wall -Wextra -Werror`.

## Final hardening

The final Stage 4 hardening assigns every new edit branch a monotonically
increasing state identity. Undo and Redo restore identities, but a new edit
after Undo never reuses the saved state's identity. The editor also synchronizes
its committed dirty state with ProgramStore and the transactional SD session
metadata, so Undo back to a saved state remains clean after restart.

## Navigation repeat backlog hardening

PicoCalc keyboard repeat events are queued by the keyboard MCU. If LCD work
takes longer than the repeat interval, repeat events can accumulate ahead of
the release event and appear to continue after the key is released. The final
navigation fast path addresses both sides of that queue:

- Left/right and wrapped-row movement update only the hardware cursor.
- A logical-line change refreshes only the primary location row.
- A viewport change remains the only navigation case that redraws source rows.
- Consecutive identical navigation repeats are collapsed while reading the
  keyboard FIFO.
- If the matching release is already queued, stale repeats are discarded.
- The first unrelated key or modifier event is deferred and preserved.
- Tiny cursor underline fills initialize only the RGB bytes actually sent.

No host-timer repeat is generated; the keyboard MCU remains the repeat source.

## Release-driven navigation burst

Hardware test feedback from Build #498 showed that per-event drawing still let
navigation remain visible after release and could interfere with the following
character. Navigation is therefore handled as one press-to-release burst:

- An unshifted arrow press enters burst mode.
- The first press and all MCU repeat events update only the editor model.
- No normal editor rows or cursor are drawn while the key remains held.
- The physical release state ends the burst; an idle timeout is only a safety
  fallback for a missed controller event.
- The final editor screen and cursor are rendered once after the burst.
- A following character remains behind the release event in the MCU FIFO and
  is read normally by the next command-input cycle.
- Shift+Up/Down page movement keeps the existing non-burst behavior.

When vertical movement changes the viewport during a burst, the LCD uses the
same VSCRSADD hardware-scroll mechanism as LIST. The three editor header rows
are temporarily fixed. Only the newly exposed top or bottom row is cleared and
given its line-number prefix; source text is filled in by the final render.
The normal editor layout is restored when the burst ends.

## Editor scroll preview correction

Build #499 target testing showed that its preview VSCRSADD definition fixed only
the top three rows. The editor status and command rows 36 through 39 therefore
joined the 456-pixel console scroll ring, and uninitialized hidden GRAM became
visible at the lower edge. The corrected preview uses an editor-only VSCRDEF:

- top fixed area: 24 pixels (rows 0 through 2);
- scrolling area: 264 pixels (rows 3 through 35);
- bottom fixed area: 192 pixels, beginning at GRAM row 288 so visible rows 36
  through 39 remain stationary and the unused remainder stays off-panel.

The normal LIST/PRINT scroll definition and software function-key overlay are
unchanged. During an arrow burst the editor erases only the old five-pixel
underline, updates the model and optional one-row body scroll, then draws the
underline at the new cursor position. The cursor therefore remains visible
during key repeat without reintroducing source-row redraws.

## Navigation rendering policy after Build #500

PicoCalc target testing showed that an editor-specific VSCRDEF still rotated
unrelated GRAM contents into the square 320-line panel and also added latency.
The editor therefore no longer performs hardware scrolling during an arrow-key
burst.

- Left, right, up, and down update only the editor model while repeat is active.
- If up/down crosses the viewport boundary, only the 12-column line-number
  prefix at the top or bottom edge is updated; the existing source text remains
  untouched as temporary visual context.
- No cursor, source row, status row, or command row is repainted per repeat.
- Key release performs one normal full editor render at the final viewport and
  cursor position.
- LIST/PRINT keeps its existing hardware-scroll implementation unchanged.
