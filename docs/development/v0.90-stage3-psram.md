# Version 0.90 Stage 3 — PSRAM Evaluation, Selective Use and Wrapped Editor

> Hardware gate: PASS on Build #490. The detected 8 MiB device passed Quick,
> Full, and Full Stress (3 passes) with matching CRC32 and zero errors. Stage 4
> continues in [`v0.90-stage4-undo.md`](v0.90-stage4-undo.md).

## Gate and scope

Stage 2 passed the PicoCalc hardware check. Stage 3 keeps every Stage 1/2
feature and adds visual wrapping, optional PSRAM detection, a destructive
diagnostic, and the evidence needed for a later adoption decision. This stage
does not publish the final v0.90 release; the Stage 3 firmware must first pass
the hardware checklist below.

CI compiled the driver and tested hardware-independent logic. Final Build #490
target evidence detected ID `0D 5D 53`, selected the corrected 25 MHz normal
Fast Read profile, and passed 1 MiB Quick, 8 MiB Full, and three 8 MiB stress
passes with matching CRC32 and zero errors.

## Wrapped full-screen editor

The editor still owns one logical-line buffer and commits through
`ProgramStore`. Long lines now occupy one or more visual rows:

`max(1, ceil(body length / 41))`

The 53-column LCD reserves a 12-column prefix so every signed 32-bit BASIC line
number fits without overwriting source text. The first visual row shows the
line number and continuation rows use a blank prefix.

- Left/Right cross visual-row boundaries naturally.
- Up/Down move by one visual row and retain a preferred visual column.
- Shift+Up/Down move by one 33-row visual page.
- Home/End remain logical-line start/end.
- Find/Goto move the visual viewport to the match or target.
- Insert/Delete/Backspace immediately reflow following visual rows.
- A 2,047-character SD body remains editable without truncation.

The old horizontal offset and logical-line vertical offset were removed. The
model now stores a `(logical line index, wrapped subrow)` top position and
exposes deterministic visual-position traversal for the renderer and tests.

Persisted empty numbered lines are retained across save/load. Direct-mode
line deletion remains a REPL action, so an editor-created `10 ` line no longer
vanishes after an SD round trip.

### Hardware follow-up

The first Build #486 hardware pass exposed visible input lag because every
cursor movement redrew the complete 40-row editor. Build #488 removes visual
row highlighting so the display shadow can skip unchanged source rows;
navigation updates only the hardware cursor and changed location characters.
Arrow repeat now uses the keyboard controller's ordered repeat/release events
instead of synthesizing host-side events that could run ahead after release.

Page Up/Down now scroll the viewport while preserving the cursor's screen row
whenever the document has enough rows. At the beginning or end it clamps to the
available document rows. F3 remains Find Next, F8 is Find Previous, and the F5
label is the explicit `INSERT LINE`.

## PSRAM evidence and electrical assumptions

Sources used for the implementation:

- ClockworkPi PicoCalc repository and mainboard schematic:
  <https://github.com/clockworkpi/PicoCalc>
- ClockworkPi PSRAM example and its pinned `rp2040-psram` submodule:
  <https://github.com/clockworkpi/PicoCalc/tree/master/Code/picocalc_helloworld>
- Upstream PIO driver, commit `419375d5af2af2c72af63cdab6c6df2c558a3a9c`:
  <https://github.com/polpo/rp2040-psram>
- AP Memory APS6404L-3SQR product/datasheet page:
  <https://www.apmemory.com/en/product/iotram/SPIQSPI>
- Raspberry Pi Pico SDK PSRAM identification logic:
  <https://github.com/raspberrypi/pico-sdk/blob/master/src/rp2_common/hardware_psram/psram.c>

PicoCalc's carrier exposes the 3.0 V APS6404L-3SQR as serial SPI, not as the
RP2350 QMI CS1/XIP device. The driver therefore uses the carrier pins and PIO.

| Signal | GPIO | Ownership in CPB |
|---|---:|---|
| PSRAM CS | 20 | PIO1 side-set |
| PSRAM SCK | 21 | PIO1 side-set |
| PSRAM MOSI | 2 | PIO1 output |
| PSRAM MISO | 3 | PIO1 input |

## Resource ownership and conflict review

| Resource | Existing owner | Stage 3 PSRAM effect |
|---|---|---|
| SPI0 | SD card | None |
| SPI1 | LCD | None |
| I2C0 GPIO6/7 | Keyboard/external I2C policy | None |
| PIO1 | CYW43 may claim a state machine | One non-fatally claimed state machine and 9 instructions |
| DMA | LCD/audio/storage paths | None; PSRAM driver is CPU-driven synchronous PIO |
| GPIO2/3/20/21 | PicoCalc carrier PSRAM | Exclusively used by PSRAM after detection |

Initialization uses `pio_can_add_program()` and a non-required state-machine
claim. If the program or state machine is unavailable, if the ID is wrong, or
if the read/write probe fails, the driver releases its PIO/GPIO resources and
CPB continues in SRAM/SD-only mode.

The selected serial clock and read phase are retained after hardware probing.
The PIO divider is recomputed after every 75/100/150/200 MHz CPU profile
change. Calls are synchronous and the Control Center cannot change CPU profile
during a diagnostic transaction.

## Detection and driver

Boot initialization performs:

1. at least 200 microseconds of power-up delay;
2. Reset Enable `0x66` and Reset `0x99`;
3. Read ID `0x9F` with the three address/dummy bytes;
4. manufacturer `0x0D`, KGD `0x5D`, and EID density decoding;
5. a saved-and-restored 16-byte read/write probe.

The public driver validates every range, divides transfers into PIO count-safe
chunks, and provides synchronous `read` and `write`. It does not replace
`malloc`, `new`, libc allocation, the BASIC workspace, or ProgramStore.

The PIO program is adapted from Ian Scott's MIT-licensed `rp2040-psram`; its
copyright and permission notice are retained in the source.

Build #486 reported `PSRAM NOT DETECTED` on PicoCalc hardware before the
read/write probe ran. The follow-up matches ClockworkPi's official example by
using the upstream settling-cycle/falling-edge read phase. Read ID is retained
as metadata, but it is no longer the sole presence gate: ClockworkPi's fixed
8 MiB carrier profile is accepted only after a reversible 16-byte read/write
probe succeeds. An absent or non-working device still fails the probe and
releases all PIO/GPIO resources.

Build #487 then reported `PSRAM READ/WRITE PROBE FAILED`. The investigation
build tests up to eight bounded profiles: 25/12.5/6.25 MHz, upstream
falling-edge/settling-cycle and normal PIO phases, and Fast Read `0x0B` with
eight dummy clocks versus Read `0x03`. Each attempt records raw ID bytes and
the first four read-back bytes from a 16-byte pattern at the end of the 8 MiB
carrier address range. It stops at the first passing profile and uses that
profile for the session. The Control Center can rerun the probe and displays
every attempted profile even when no profile succeeds.

Build #489 hardware results returned `AB 54 01 FF` for the expected probe
prefix `55 AA 00 FF` on every profile. This is the expected signature of a
one-bit left shift with the idle-high bus filling the final bit, proving that
the device accepted writes but the PIO read loop discarded the first data bit.
The normal-phase receive path now pre-decrements its bit counter while SCK
remains low, then samples the first data bit on the immediately following
rising edge instead of generating an extra clock before the first sample.

## Diagnostic and benchmark

Control Center contains `PSRAM Diagnostics`:

- **Quick test:** first 1 MiB.
- **Full detected capacity:** all detected bytes.
- **Full stress:** three consecutive full-capacity passes, stopping on error.

Both are explicitly destructive to PSRAM contents. BASIC source remains in
SRAM or SD and is unaffected. The diagnostic runs:

- full-range `00`, `FF`, `AA`, and `55` write/read verification;
- walking-one and walking-zero samples at the beginning, middle, and end;
- deterministic address-dependent data, byte comparison, and CRC32;
- sequential write/read benchmarks at 1, 16, 64, 256, and 1,024 KiB;
- 256 four-byte pseudo-random write and read/verify operations per size.

The result screen reports tested size, first failing address, stage, error
count, CRCs, full-range throughput, size-specific sequential throughput, and
random operations per second. Results are runtime observations and are not
saved as fabricated source constants.

## Selective-use decision

Stage 3 deliberately reports **0 KiB runtime PSRAM use**. System Information
shows detection, capacity, PIO state machine, bus clock, and this zero-use
status.

The candidates were evaluated as follows:

| Candidate | Decision before hardware benchmark | Reason |
|---|---|---|
| Current editor line buffer | Keep in SRAM | 2,048 bytes, latency-sensitive, already bounded |
| Undo/redo history | Defer | Not required for v0.90 and needs measured latency/reliability |
| Wrapped-row cache | Reject for now | Visual traversal is deterministic and bounded without a cache |
| Clipboard | Defer | No Stage 3 clipboard UI |
| Directory cache | Reject for now | Existing bounded root listing already works |
| Search index | Reject for now | Current linear Find avoids coherence and memory ownership risk |

Adoption is allowed only after actual hardware results show a clear user
benefit with no regression at all CPU profiles. Absence or failure of PSRAM
must remain a fully supported fallback.

### CI memory evidence

The Stage 3 firmware was measured with the same Pico SDK 2.3.1 CI toolchain as
the Stage 2 firmware. The driver and diagnostics add 9,820 bytes to the flash
load image while the wrapped editor and PSRAM state add only 40 bytes to the
static SRAM sections. `Repl`, `EditorModel`, and `FullScreenEditor` object
sizes are unchanged from Stage 2.

| Item | Stage 2 | Stage 3 | Delta |
|---|---:|---:|---:|
| Flash load image | 1,089,724 | 1,099,544 | +9,820 |
| `.text` | 561,896 | 570,308 | +8,412 |
| `.rodata` | 356,800 | 358,208 | +1,408 |
| `.data` | 170,956 | 170,956 | 0 |
| `.bss` | 183,468 | 183,508 | +40 |
| `.data + .bss` | 354,424 | 354,464 | +40 |
| Static SRAM sections | 354,712 | 354,752 | +40 |

These figures cover static allocations and compiler-estimated stack frames.
Runtime heap and stack high-water marks remain part of the hardware check.
