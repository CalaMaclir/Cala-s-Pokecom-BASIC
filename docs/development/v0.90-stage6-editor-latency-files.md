# Version 0.90 Stage 6 — Editor Latency R2 / FILES Filename Handling

## Scope and branch basis

Stage 6 is based on `v0.90` commit
`b2e24c4ee935edf2486743e5a7900ec81e1f31e6`. Stage 5 audio PR #41 was
still open when this branch was created, so no Stage 5 change is included.

This stage changes editor navigation/layout work and root filename handling. It
does not change BASIC syntax, logical line limits, visual wrap width, safe-file
transactions, audio, CPU profiles, Bluetooth pairing, I2C timing, or USB MSC
ownership.

## Editor: previous call graphs and root causes

### Single arrow and built-in repeat before Stage 6

```text
platform::get_char()
  -> display::set_cursor_visible(false)
  -> FullScreenEditor::navigation_burst_step()
     -> EditorModel::move_left/right/up/down()
        -> ensure_visual_cursor_visible()
           -> visual_screen_row()
              -> next_visual_position()
                 -> visual_row_count()
                    -> line_view()
                       -> EditorDocument::read_line()
                          -> ProgramStore::read_line_text()
  -> platform::collect_navigation_burst()
     -> repeat callback -> navigation_burst_step()
  -> FullScreenEditor::render_full()          (unconditional)
     -> render_header()/render_location()
     -> 33 * render_visual_row()
        -> line_view()/read_line_text()
     -> message and two function-key rows
```

A short press therefore waited for the built-in keyboard burst collector to
observe release and then entered a complete logical redraw. LCD text shadowing
could suppress unchanged SPI pixels, but only after EditorModel traversal,
string construction, and ProgramStore accesses had already happened.

Classic HID, BLE HID, and terminal arrows normally do not report
`navigation_key_held()`; the collector returns immediately, but the same
unconditional `render_full()` still occurred.

### SD body-read path before Stage 6

For a non-current logical line, `visual_row_count()` called `line_view()`.
The SD adapter then used:

```text
storage::init / try_lock
fopen(work file)
fseek(entry.offset)
fgets
length + line-number + hash verification
fclose
storage::unlock
```

That path was correct for consuming source text, but unnecessary for layout,
which only needs line number and body length already stored in the SD index.

### Previous viewport behavior

`visual_screen_row()` started at `visual_top_` and advanced up to 33 visual
rows to find the cursor. `ensure_visual_cursor_visible()` invoked that scan
after ordinary movement. At burst completion, the editor redrew the complete
viewport even when neither `visual_top_` nor the displayed source changed.

## Editor: Stage 6 design

### Metadata-only layout API

`EditorDocument::line_metadata()` and
`ProgramStore::read_line_metadata()` return only line number and body length.

- RAM reads the existing `ProgramLine` entry directly.
- SD reads `SdProgramStore::Entry.number` and `Entry.length`.
- SD metadata reads do not lock storage, open the work file, seek, copy source,
  or calculate a hash.
- A suspended/not-ready SD store still fails through `ProgramStore::ready()`.
- Actual body reads retain line-number, length, offset, and hash verification.

`visual_row_count()`, next/previous visual-position traversal, page layout,
viewport normalization, and line-location scans use metadata. The current
logical line uses the EditorModel working-buffer length so unsaved reflow is
visible immediately.

### Cursor screen-row invariant

EditorModel now owns:

```text
cursor_screen_row_
cursor_screen_row_valid_
```

When valid:

```text
cursor_screen_row_ < visible_lines_
advance(visual_top_, cursor_screen_row_) == current_visual_position()
```

Ordinary one-step movement updates this state incrementally:

- movement inside the same wrapped row leaves it unchanged;
- movement to an adjacent visible row increments/decrements it;
- movement below the viewport advances `visual_top_` once and keeps the
  cursor on the last screen row;
- movement above the viewport sets `visual_top_` to the new row and keeps the
  cursor on row zero.

The bounded reference scan remains in `visual_screen_row()` for tests,
fallback synchronization, and layout-changing operations. It is allowed after
begin, Home/End, page movement, Find/Goto, insert/delete, Undo/Redo, line
insertion/deletion, and wrap reflow. Normal Left/Right/Up/Down does not call it.

Changing logical lines commits a dirty old working line, loads exactly the new
logical line into the working buffer, and updates the cached screen row as the
same adjacent visual step. Layout metadata does not cause additional body
reads.

### New navigation and rendering path

```text
arrow event
  -> O(1) EditorModel step
  -> O(1) cached screen-row step
  -> hide old underline
  -> set cursor position
  -> show new underline
```

The display keeps the existing underline implementation. Stage 6 only exposes
`platform::set_cursor_visible(bool)`; hardware scrolling is not used.

The first press is applied and painted before entering
`collect_navigation_burst()`. During a burst, model steps are never dropped.
Cursor painting is limited to at most once per 25 ms. Background service calls
and the pending-command-key behavior remain owned by the existing collector.

If a repeat crosses a viewport edge, the editor may update the affected
12-column line-number prefix. It does not draw body rows during the burst.
After release:

- unchanged viewport: refresh location rows and the final underline only;
- changed viewport: perform one final complete render;
- full renders during repeat: zero;
- complete renders after release: at most one.

### SD viewport batch read

`ProgramStore::visit_line_range()` visits a contiguous logical-line range.

For SD it uses one storage lease, one `fopen`, one `fclose`, and the
existing reusable SD scratch buffer. Every visited entry is still checked
against its indexed offset, line number, body length, and hash. RAM visits its
array directly. A callback must consume the borrowed body before it returns.

`render_full()` determines the logical range covered by the 33 visual rows
from metadata, then calls this API once. Multiple wrapped rows from one logical
line reuse the one visited body. If that line is the current edit line, the
EditorModel working buffer is rendered instead of the persisted body.

No second 53-by-33 character cache and no PSRAM allocation were added.

### Fast-path fallback conditions

The editor falls back to bounded synchronization/full rendering when layout or
screen identity can change non-locally: page movement, Home/End, Find, Goto,
insert/delete/backspace, Insert/Delete Line, Undo/Redo, save/prompt return, or
an error. These operations are not the ordinary arrow-key hot path.

## Editor performance instrumentation

`RMB_EDITOR_PERF` is a compile-time option and is off in the normal build.
When enabled, small counters record:

- editor key events and navigation steps;
- model and cursor-paint time;
- maximum model step latency;
- viewport scans;
- metadata and body reads;
- SD work-file opens;
- full renders and body-row renders;
- burst duration and repeat count.

There is no hot-path `printf`. The editor writes two serial summary lines once
when it exits. Release builds compile the counter calls to no-ops and do not
allocate the counter object. CI builds an additional
`CPokecombasic-editor-perf.uf2`; the ordinary UF2 has no performance logging.

Target hardware results are intentionally not invented. All latency and
counter targets remain NOT YET HARDWARE VERIFIED until the performance UF2 is
run on PicoCalc.

## FILES: previous call graphs and exact causes

### LOAD/RUN/EDIT selection

```text
FILES [PROGRAMS]
  -> selected_name (complete directory entry)
  -> ENTER: load_named_program(selected_name, false)
  -> R:     load_named_program(selected_name, true)
  -> E:     storage::load_program(selected_name, ProgramStore)
  -> ProgramStore::load()
  -> ProgramStore::normalize()
```

The menu did not construct a textual `LOAD ...` or `RUN ...` command and
did not pass the selection back through the REPL tokenizer. The complete
selection was already dispatched directly.

The exact `BAD FILENAME` cause was
`SafeFileWriter::valid_root_name()`: its allow-list omitted ASCII space.
A second defect existed in `storage::make_path()`, used by
`program_exists()`: it explicitly stopped copying at the first space. This
could make overwrite checks inspect `MY.BAS` for `MY PROGRAM.BAS`.

### Rename before Stage 6

```text
FILES N
  -> LineEditor result
  -> storage::rename_root_file(old_name, new_name, current_filename)
  -> file_management::rename_file()
  -> SafeFileWriter::valid_root_name(source and destination)
  -> std::rename()
```

Both source and destination reached the same space-rejecting validator.
PROGRAMS rename also lacked the ProgramStore-style `.BAS` completion.
A loaded named source was treated as protected even though active SD editing
uses an independent internal `RMBPxxxx.BAS` work file.

## FILES: Stage 6 filename policy

All program-name paths share `file_management::normalize_program_name()`.

Allowed:

- ASCII alphanumeric, underscore, hyphen, period, and internal ASCII space;
- repeated internal spaces;
- names with `.BAS` in any case;
- names without the extension, which receive exactly one `.BAS`.

Rejected:

- null/empty and all-space names;
- leading or trailing space;
- leading or trailing period under the existing policy;
- `..` anywhere under the existing conservative policy;
- slash or backslash;
- controls, DEL, NUL, and characters outside the existing allow-list;
- names longer than the 79-character storage limit;
- ProgramStore work names, editor/session/transfer staging names, configuration
  and session names where the existing guard applies.

No input is silently trimmed. Root-only path construction remains in place.
Internal-space support does not enable directories or path traversal.

FILES PROGRAMS continues to dispatch the already selected complete value
directly for LOAD/RUN/EDIT. Rename normalizes only the destination in PROGRAMS
mode; DIRECTORY mode retains its literal root-file behavior.

When the loaded named source is renamed, its ordinary in-use guard is bypassed
only for that exact source; intrinsic reserved/staging guards remain active.
The filesystem rename is followed by a ProgramStore session-name update. If
session update fails, the UI uses an explicit recovery-only rename to restore
the missing current name; all normal calls still reject an in-use destination.
The active internal work filename remains protected by
`program_files::in_use()`.

Destination-exists behavior remains non-destructive: rename returns
`FILE EXISTS` and no overwrite occurs. The UI therefore has an implicit safe
Cancel policy; Stage 6 does not add overwrite-on-rename.

Case-only rename remains a known limitation. The case-insensitive equality
guard reports `FILE EXISTS`; no temporary intermediate name is introduced in
this stage.

## Tests

Host tests cover:

- metadata number/length in RAM and SD, empty bodies, bounds, and 2047 bytes;
- cached cursor screen row versus the bounded reference scan for lengths
  0, 1, 41, 42, 82, 100, 500, 1000, and 2047;
- Left/Right and same-line Up/Down with zero document body reads;
- adjacent logical-line movement with exactly one new-line body read;
- range visits in RAM and SD, range-end clamping, empty and long bodies;
- legal internal-space names and rejected leading/trailing space, traversal,
  separators, controls, and empty names;
- byte-preserving rename with spaces;
- `.BAS` completion without double extension;
- existing editor wrap/history, storage transaction/recovery, safe-file,
  USB ownership, display, audio, Bluetooth, and runtime suites through the
  repository workflow.

The performance build provides target-only counters for the redraw/open limits.
No target result is marked PASS from host testing.

## Hardware verification checklist

All items below are NOT YET HARDWARE VERIFIED.

1. Single and held Left/Right on short lines.
2. Single and held Up/Down within and across logical lines.
3. No post-release extra movement, stale underline, or missing cursor.

5. Insert/Delete Line and Undo/Redo.
6. 41, 42, 100, 500, 1000, and 2047-character wraps.
7. Viewport top/bottom transitions without reordered or duplicated rows.
8. INTERNAL RAM and SD CARD edit/save/reload, including empty numbered lines.
9. Built-in, Classic HID, BLE HID, and terminal arrows.
10. `MY PROGRAM.BAS` LOAD, RUN, and EDIT from FILES.
11. Space/no-space source and destination rename combinations.
12. Rename content equality, list refresh, existing destination, reserved names,
    leading/trailing spaces, separators, and extension completion.
13. WAV/PLAY coexistence, Bluetooth, Wi-Fi, board LED, USB MSC return, PSRAM
    Undo/Redo, SD removal, and USB-owned rename rejection.
14. CPU profiles 75, 100, 150, and conditionally available 200 MHz.
15. Performance counters: in-viewport Left/Right has zero body reads, SD opens,
    viewport scans, full renders, and body-row renders.
16. Same-line Up/Down has zero body reads, SD opens, and full renders.
17. Repeat has zero full renders; release has at most one.
18. One SD viewport render has at most one work-file open/close.
19. First visible response target: 30 ms or less.
