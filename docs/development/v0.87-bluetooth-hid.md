# Version 0.87 Bluetooth Classic HID Keyboard

Version 0.87 adds one Bluetooth Classic HID keyboard as a second input
device while preserving the Version 0.86 Bluetooth Classic SPP transport.

## Architecture

- `bluetooth_serial.cpp` remains the RFCOMM/SPP owner.
- `bluetooth_hid_keyboard.cpp` owns Classic inquiry, HID Host connections,
  HID descriptor parsing, keyboard authentication, and reconnect.
- `bluetooth_hid_keyboard_core.cpp` is hardware-independent. It maps HID
  usages to existing CPB key codes, handles modifiers/Caps Lock, US/JIS
  layouts, and host-side repeat.
- `unified_keyboard.cpp` merges the PicoCalc I2C keyboard and Bluetooth HID
  queues before the platform input APIs.
- `bluetooth_device_registry.cpp` stores explicit SPP/HID profile metadata
  separately from BTstack link keys. Existing Version 0.86 pairings without
  metadata are treated as SPP.

No new key-code namespace is introduced. Bluetooth keys use the same codes as
the internal keyboard for F1-F10, arrows, Home, End, Delete, BREAK, screenshot,
and standby.

## BTstack pools

The Version 0.86 limits are retained:

- `MAX_NR_HCI_CONNECTIONS=2`: one SPP ACL plus one HID ACL.
- `MAX_NR_HID_HOST_CONNECTIONS=1`: the supported single keyboard.
- `MAX_NR_L2CAP_CHANNELS=4`: RFCOMM plus HID Control and Interrupt, with one
  spare slot.
- `MAX_NR_L2CAP_SERVICES=3`: RFCOMM plus the two HID PSM services.
- `MAX_NR_RFCOMM_CHANNELS=1`: unchanged SPP channel.

Increasing these pools without a measured need would consume SRAM and is not
required for the intended SPP + HID topology.

## Pairing and security

Keyboard discovery is user-initiated from Control Center. Unknown devices are
not bonded outside that flow. Class of Device is used only as a display and
ordering hint because commercial keyboards do not always advertise it
correctly.

Legacy keyboard PIN pairing generates a six-digit code and sends it to the
keyboard through BTstack. SSP passkey notification/confirmation displays the
same six-digit workflow. The SPP pairing path keeps its Version 0.86
No-Input/No-Output behavior. Because Classic authentication controls are
global, starting a new HID pairing session requires SPP pairing to be closed
and an active SPP console to be disconnected. Once both devices are bonded,
one SPP link and one HID keyboard link may coexist and reconnect together.

Deleting a device removes its BTstack link key, saved name, and profile
metadata. Deleting all pairings clears all three stores.

## Control Center organization

Control Center presents one `Pair New Device...` entry for all new
Bluetooth pairings. The next screen asks whether the new device is a
`Computer / Serial` peer or a `Keyboard`:

- Computer/Serial pairing keeps CPB discoverable while the computer initiates
  the bond.
- Keyboard pairing scans from CPB, lets the user select a device, and then
  performs the HID passcode flow.

The common entry point is a UI organization only. The SPP and HID state
machines, security capabilities, and profile metadata remain separate, and
only one new-device pairing flow may run at a time.

Classic and BLE keyboards share one live-list screen: discovery
continues while the list is visible, names update in place, Up/Down scroll,
Enter selects, and ESC stops. Serial/SPP is initiated by the remote device and
therefore cannot show a local discovery list; its pairing screen uses the same
header, status, time, and ESC-stop presentation.

All post-pairing operations are collected under `Paired Devices...`.
Profile-labelled entries provide connect/wait, disconnect, and forget actions.
Keyboard reconnect and disconnect are therefore not duplicated in a separate
keyboard menu. The JIS/US keyboard layout remains directly selectable from the
Bluetooth top-level menu.

## Layouts and input behavior

The default Bluetooth layout is JIS and may be changed to US in Control
Center. JIS handling includes the physical keys for `@`, `:`, brackets,
backslash/Yen, underscore, and caret. CPB is ASCII, so the Yen key produces
ASCII backslash, matching the conventional Japanese encoding/display
relationship.

Repeat starts after 400 ms and repeats every 50 ms for printable keys,
Backspace, Delete, arrows, Home, and End. Function keys, modifiers, Caps Lock,
and global hotkeys do not repeat.

Interactive Bluetooth HID input follows the configured Key Click setting.
Runtime input does not click, matching the existing internal-keyboard policy.

## Standby

Bluetooth-keyboard wake is not part of the initial Version 0.87 scope. The
radio is stopped before standby, the prior Bluetooth ON state is restored
after an internal/serial wake, and bonded HID/SPP devices can reconnect.

## Host tests

CI covers:

- US and JIS usage mapping
- Shift, Ctrl, Alt hotkeys, and Caps Lock
- Function/cursor key mapping
- repeat delay, interval, and key-up cancellation
- profile/name upsert, lookup, deletion, and clearing

Firmware CI also rebuilds Version 0.86 and writes the Flash/SRAM/BSS/DATA and
stack comparison into the downloadable artifact.


## BLE keyboard staged implementation

The BLE keyboard work is deliberately split so that the first hardware test does
not lock the project into a partial HOGP implementation.

### Step 1 — diagnostic BLE scan (implemented)

`bluetooth_hid_ble_keyboard` performs an active LE scan until the user presses
ESC or selects a device, and keeps up to 64 advertisements. The device list is
visible while scanning continues. Newly discovered devices are added in place;
when a scan response supplies a previously unknown name, only that row is
redrawn. RSSI-only changes do not trigger repainting. Lists longer than 18
rows are navigated with the existing scrolling selection model; a `+` marker
reports that the 64-device diagnostic capacity was reached. The UI shows name, RSSI, public/random address type, and address. To reduce
noise, the visible list contains only advertisements that expose HID Service
UUID 0x1812 or Bluetooth Keyboard Appearance 0x03C1. Other advertisements may
be retained briefly as an internal name/scan-response cache but are not
selectable.

Menu path:

`Control Center > Bluetooth > Pair New Device > Pair Keyboard (Classic / BLE)`

### Step 2 — pairing and Boot Keyboard reports (implemented)

The selected LE device is connected as a central, bonded with the Security
Manager, and queried for HID Service 0x1812. The implementation enables the
Boot Keyboard Input Report characteristic and routes its eight-byte reports
through the same `KeyboardCore` used by Classic HID. JIS/US layout, Caps Lock,
Shift, key repeat, and the 32-entry input queue therefore behave consistently
across the internal, Classic, and BLE keyboards.

Step 3 extends this path with HOGP Report Protocol, retaining Boot Protocol
as the fallback.

Pairing uses Display Only IO capability with Secure Connections support, MITM
protection, and bonding. The shared configuration function explicitly calls
`sm_set_secure_connections_only_mode(false)` after `sm_init()` and before every
new connection. Secure Connections remains preferred when both peers support
it, while legacy passkey pairing is permitted with 16-byte keys.

#### Authentication failure and retry review (builds 446/447)

The SDK is pinned to Pico SDK 2.3.1, whose BTstack submodule is
`eb0bb8b5ea6d234ccb940313b47f7a5c3b4e20ec`. In that version, `sm_init()` sets
`sm_sc_only_mode = true` when LE Secure Connections is compiled in. Changing
AuthReq flags does not change that separate policy. Builds 446/447 removed the
SC flag but left SC-only mode enabled; the stack rejects a negotiated legacy
pairing with Authentication Requirements (SMP 0x03). Adding MITM alone could
not fix this contradiction. The earlier assertion that 0x03 uniquely proved
a peer MITM requirement was incorrect; it is a broader authentication failure.

New pairing still removes only the bond matching the selected address/type.
Failure messages retain the SMP reason rather than claiming retry will fix it.
There is no automatic security downgrade/reconnect loop. Passkey display
starts a fresh 60-second input window.

Failure/cancellation retains the connection state until the asynchronous
disconnect/cancel-completion event. A connection succeeding concurrently with
cancellation is explicitly disconnected. New scanning/connecting is blocked
during teardown; late SM events cannot restart GATT discovery after failure.
After failure and teardown, Enter returns to scanning; ESC goes back.

A new scan retains previously identified HID names/classifications but resets
their per-scan observation flags. Only devices advertising again in that scan
are visible; old cached rows are not presented as newly found devices. A known
keyboard is recognized by the same address and address type even if its new
advertisement omits the HID UUID/Appearance. Active scanning disables duplicate
filtering so subsequent scan responses can update names.

Hardware observation: after 0x03, the keyboard did not reappear until its power
was cycled. This does not prove whether advertising stopped or its contents
changed. CPB cannot restart advertising on a disconnected remote device.
The failure screen therefore advises re-entering pairing mode, then restarting
the keyboard if still absent. A changed random address cannot safely be matched
to a previous candidate by name alone.

Host regression tests compile the production security, discovery, and recovery
functions against mocked radio APIs. They cover the SC-only default, retained
classification with fresh-observation gating, 64-entry capacity, normal
disconnect, cancel/connect races, and scan exclusion during teardown. Actual
pairing, over-the-air advertisements, and keyboard input still require hardware
validation.

### Step 3 — registry, Report Protocol, and reconnect (implemented)

The pinned SDK's `hids_host` reads Report Map and Report Reference descriptors
and enables Report Protocol input notifications. The report adapter handles
Report IDs, ID-less descriptors, modifier bits and keyboard arrays/bitmaps.
Truncated and unrelated reports are ignored; consumer/mouse reports do not
release keyboard keys. Input still uses the shared six-key `KeyboardCore`.
If HIDS discovery fails or supplies no keyboard input descriptor, the existing
Boot Keyboard path runs after the HIDS callback has finished. A connection-ready
message means setup completed, not that a physical keypress has been verified.

`Paired Devices` combines Classic link keys and saved LE encryption keys, up to
32 rows with scrolling. BLE rows show `KEYBD LE` and live ON/OFF state. Enter
opens Connect Keyboard / Disconnect / Forget. Reconnect preserves the existing
bond; only Pair New Device requests a fresh pairing. This is an explicit user
reconnect, not an automatic background retry loop. Reconnect to peers changing
private addresses remains subject to the controller's identity resolution and
must be tested on hardware.

The registry v2 includes address type (Classic, LE public, LE random), so equal
numeric addresses cannot overwrite/delete another transport's metadata. V1
Classic metadata is read and migrated on the next write, without changing link
keys. Reconnect does not rewrite unchanged metadata. Full metadata storage
reports a save failure rather than evicting another device. Pairing keys remain
in BTstack's separate flash-backed databases. Previously saved LE bonds without
names (including build 448) are listed as `BLE keyboard`; successful subsequent
connections can fill the name. Known SPP cross-transport derived keys are not
shown as extra keyboards.

One `Pair Keyboard (Classic / BLE)` entry starts both discovery transports and
renders a combined, scrolling live list. Rows carry transport and address type;
selection follows that identity as results arrive. Both scans stop before a
connection or ESC. Name updates repaint only affected rows. Only discovery may
overlap; Classic and BLE keyboard connections remain mutually exclusive.
BLE HID advertisement filtering remains in effect; Classic keeps its previous
keyboard-first candidate ordering.

Host regression tests cover transport/type identity isolation, registry v1/v2
migration, non-destructive capacity limits, unchanged reconnect writes, and
report decoding against the SDK's real HID parser. Existing security/cancel/
rediscovery tests and the firmware build remain mandatory. Key input, combined
radio discovery, reconnect and individual removal require hardware validation.

The separate BLE transport API and shared `KeyboardCore` are the extension
points for this work; callers do not depend on the current GATT query states.

### Step 4 — coexistence and release hardening (implemented)

The final hardening separates a fresh keyboard pairing from reconnecting an
already bonded keyboard. Opening a new keyboard bond still requires the SPP
link to be disconnected because it changes shared authentication policy.
A registered Classic or BLE keyboard may reconnect while SPP is connected;
`MAX_NR_HCI_CONNECTIONS=2` reserves one ACL for each. Neither keyboard may
connect while the Serial pairing window is open. Classic and BLE discovery may
run together in the unified list, while connection, authentication, and active
keyboard states remain mutually exclusive.

An unexpected BLE link-close resets the parser, input queue, GATT/HIDS state,
connection handle, and UI state to disconnected. The saved bond and registry
record remain available for a manual reconnect from `Paired Devices`. An
explicit Disconnect follows the same teardown but does not delete the bond.
The firmware does not continuously retry a powered-off keyboard in the
background; this avoids occupying the second ACL and interfering with SPP.

The regression suite now covers:

- SPP-connected policy: fresh keyboard pairing rejected, bonded reconnect allowed;
- Serial pairing window exclusion for Classic and BLE reconnect;
- concurrent Classic/BLE discovery and exclusive connection states;
- authentication failure, connect/cancel races, unrelated disconnect events,
  unexpected ready-link loss, and clean retry state;
- Report Protocol with ID, without ID, array and bitmap keyboards, truncated
  input, consumer-report isolation, and Boot fallback;
- registry migration, transport/address-type isolation, individual deletion,
  and reconnect without redundant flash writes;
- complete firmware CI plus flash, SRAM, BSS/DATA, and compiler stack reports.

Build 450 hardware verification passed BLE registry display, BASIC key input,
and disconnect followed by manual reconnect. Build 451 then passed all Step 4
release-candidate hardware checks:

1. With an SPP console connected, the saved BLE keyboard reconnected and
   simultaneous console and keyboard input worked.
2. After the keyboard was powered off during input, its row changed to OFF;
   powering it back on and reconnecting from `Paired Devices` restored input.
3. The corresponding saved Classic-keyboard coexistence check passed.
4. Cancelling the combined discovery list with ESC left SPP usable, and a
   subsequent scan started normally.

Together with the complete CI pass for build 451, these results complete the
planned BLE keyboard Steps 1 through 4.

### Resource and coexistence policy

The firmware keeps `MAX_NR_HCI_CONNECTIONS=2`: one SPP connection and one
keyboard connection. Classic HID and BLE HID are mutually exclusive. SPP must
be disconnected before a new keyboard pairing attempt, but can remain connected
when reconnecting a saved keyboard. BLE bond
keys use BTstack's flash-backed LE device database and are cleared by
`Forget All Paired Devices`; individual BLE entries can also be deleted from
`Paired Devices`, without removing other Classic or BLE keys.
