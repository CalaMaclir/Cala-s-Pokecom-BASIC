# Version 0.91 Stage 3 — Runtime Memory & Compile Cache

## Purpose

Stage 3 completes the runtime-memory work started in Stage 2.

The design keeps the same rule:

- PSRAM is persistent/cached backing storage.
- Internal SRAM is the active execution working set.
- VM opcode fetches and hot runtime data never execute directly from PIO PSRAM.

Stage 3 targets two remaining persistent objects:

1. direct-mode scalar state;
2. the approximately 34 KiB `CompiledProgram` workspace.

## DirectState

Before Stage 3, `VM` permanently contained 64 `DirectScalar` records, about
9.5 KiB, so direct-mode variables could survive between statements.

Stage 3 removes that fixed array from `VM`.

Direct-mode state now uses:

- PSRAM client: `DirectState`;
- one approximately 9.5 KiB serialized snapshot in PSRAM when available;
- dynamic internal-SRAM fallback if PSRAM cannot be claimed;
- a temporary SRAM working copy only while a direct statement containing
  symbols is executing.

Boundary policy:

```text
direct statement begins
        |
        v
PSRAM/SRAM snapshot -> transient SRAM DirectState
        |
        v
restore symbols -> execute VM in SRAM
        |
        v
save symbols -> transient DirectState
        |
        v
transient SRAM DirectState -> PSRAM/SRAM snapshot
```

Statements without symbols do not allocate the temporary DirectState working
copy.

`CLEAR` and `NEW` release the persistent DirectState allocation.

PSRAM reprobe/destructive diagnostics intentionally remain blocked while
persistent direct variables exist. The user can execute `CLEAR` before a
destructive PSRAM diagnostic.

## Transient CompiledProgram

Before Stage 3, `Repl` permanently embedded one `CompiledProgram` even when
BASIC was idle.

ARM size:

- `sizeof(CompiledProgram)`: 33,944 bytes.

Stage 3 removes the persistent object from `Repl`.

RUN/direct execution now:

1. acquires the existing foreground compile-workspace lease;
2. allocates one `CompiledProgram` in internal SRAM;
3. compiles/restores IL;
4. executes the VM from that internal-SRAM object;
5. destroys and frees the workspace on every exit path.

The existing `workspace_busy_` invariant still prevents nested/reentrant
compilation. `active_compiled_` is non-null only while a workspace exists.

Allocation failure reports `OUT OF MEMORY`.

## PSRAM Compiled Program Cache

Stored-program RUN adds a PSRAM compiled cache.

Direct statements are deliberately not cached.

The cache stores the meaningful parts of `CompiledProgram` explicitly:

- VM opcodes;
- numeric literal pool;
- string literal pool;
- symbols;
- complete line map, including the extended line map used by SD programs over
  256 lines.

The native `extra_lines` pointer itself is never serialized.

Cache data has a versioned header and CRC32 payload validation.

### Cache key

`ProgramStore` now maintains a monotonic 64-bit source revision.

The revision changes only when source contents or active source identity are
replaced/modified. Saving or renaming an unchanged program does not invalidate
compiled IL.

RUN behavior:

```text
RUN
 |
 +-- source revision matches valid PSRAM cache
 |       |
 |       +-- restore + CRC32 verify
 |       +-- PSRAM -> SRAM CompiledProgram
 |       +-- VM run
 |
 +-- cache miss/stale/corrupt
         |
         +-- compile into SRAM CompiledProgram
         +-- serialize verified result to PSRAM
         +-- VM run
```

The VM never executes opcodes directly from PSRAM.

A revision mismatch rejects and releases stale compiled cache immediately.
Background servicing also drops stale cache as soon as it observes a source
revision change.

Cache failure is non-fatal: normal SRAM compile/run remains available.

## PSRAM clients after Stage 3

The allocator clients are:

- Editor History
- Program Store
- SD Cache
- Direct State
- Compiled Cache
- Audio Cache (reserved for future use)

The final 16-byte PSRAM hardware-probe tail remains unavailable to clients.

System Information reports:

- total PSRAM runtime allocation;
- Editor History / Program Store / SD Cache;
- Direct State / Compiled Cache;
- SD cache hit/miss counters;
- compile cache VALID/EMPTY state and hit/miss counters;
- DirectState PSRAM/SRAM fallback state.

The SD read cache and compiled cache are disposable and are released before a
PSRAM reprobe/destructive diagnostic. Editor history, ProgramStore, and
DirectState retain their normal ownership semantics.
