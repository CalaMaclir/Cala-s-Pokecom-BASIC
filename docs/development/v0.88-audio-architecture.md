# Version 0.88 development — PicoCalc PWM audio architecture

## Hardware result that changed the design

Build 457 tested the high-carrier PIO hypothesis on a real PicoCalc:

- PCM rate: 22050 Hz;
- PIO carrier: about 352.8 kHz;
- 16 carrier cycles per PCM frame;
- seven-bit base duty plus persistent fractional error diffusion;
- tested at 150, 100, and 75 MHz.

The real `AUTORUN.WAV` playback did not improve at any CPU clock. Earlier
hardware tests also found no useful improvement from either approximately
250 kHz / 8-bit PWM or approximately 22.05 kHz / high-resolution PWM.

This is negative but decisive evidence: carrier frequency alone is not the
primary cause of the reported distortion. The PIO design is therefore removed
rather than retained as an unverified complexity and RAM cost.

## Source and transport evidence

The supplied startup audio and its PicoCalc recording establish the following:

- input: valid RIFF/WAVE, 22050 Hz, signed 16-bit little-endian, stereo;
- 42487 frames, 1.92685 seconds, and 169948 PCM data bytes;
- no PCM clipping or material DC offset;
- the WAV is sample-aligned with the supplied AIFF conversion;
- hardware recording duration matches the source;
- no sustained gaps indicate a persistent SD/output underrun;
- the CPB recording has severe level-dependent harmonic distortion.

The same PicoCalc and the same AUTORUN.WAV were then tested with the official
PicoCalc PicoMite firmware. Playback was clean at maximum PicoMite volume,
although its perceived level was substantially lower. This confirms that the
file, GP26/GP27 board routing, analogue filter, amplifier, headphone path, and
speaker are capable of normal playback. The remaining fault is specific to
CPB's digital PWM output path or its pad/peripheral state.

## Reference implementation

ClockworkPi's PicoCalc repository includes PicoMite configured for GP26 and
GP27. Its PWM output uses:

- hardware PWM slice 5, channels A and B;
- approximately 44.1 kHz PWM for normal audio;
- a high-resolution wrap derived from the system clock;
- PCM samples held for repeated PWM periods when the source rate is low;
- direct writes of left/right levels to the PWM compare register.

For a 22050 Hz WAV, PicoMite selects 44100 Hz and repeats each PCM frame twice.
It also updates both PWM compare channels from the wrap interrupt and explicitly
selects slow GPIO slew. The successful same-device test makes these observable
output conditions the relevant reference.

Only the behavior is used as a specification. CPB's implementation, names,
buffer consumer, conversion helpers, and tests are independently written; no
PicoMite source code or volume table is copied.

## Selected architecture

Version 0.88 now uses an independently written wrap-IRQ consumer while
retaining CPB's asynchronous producer and six-buffer FIFO.

| Item | Previous PIO build 457 | Current design |
| --- | ---: | ---: |
| PCM engine | 22050 Hz | 22050 Hz |
| PWM carrier | about 352.8 kHz | about 44.1 kHz |
| PCM hold | 16 dithered cycles | 2 identical PWM periods |
| Amplitude | 7-bit base + temporal dither | signed PCM to 12-bit logical code |
| Transport | two PIO SM + two DMA | hardware PWM wrap IRQ |
| Channel update | separate channel transfers | one atomic stereo register write |
| Words/PCM frame | 2 | 2 |
| Output-buffer SRAM | 49152 bytes | 49152 bytes |

The carrier and logical PCM rates remain distinct. Each decoded 22.05 kHz
frame becomes two identical packed compare words. The 44.1 kHz wrap handler
consumes one word and updates both channels atomically on each interrupt.

### Clock profiles

The PWM divider is 1. The period is the integer quotient of the live system
clock and 44100 Hz:

| CPU clock | Wrap | Carrier |
| ---: | ---: | ---: |
| 75 MHz | 1699 | 44117 Hz |
| 100 MHz | 2266 | 44111 Hz |
| 150 MHz | 3400 | 44104 Hz |

All profiles differ from 44.1 kHz by less than 0.04 percent. Signed PCM is
first expressed as an independently implemented 12-bit logical code and then
scaled to the live PWM wrap.

## WAV pipeline

The WAV producer remains independent of the output backend:

1. a 4096-byte read-ahead buffer performs sequential stdio reads;
2. PCM decode handles 8-bit unsigned and 16-bit signed little-endian samples;
3. mono is duplicated and stereo is stepped as left/right frames;
4. the phase accumulator converts 11025, 22050, or 44100 Hz to 22050 Hz;
5. volume, tail fade, and key-click mixing produce signed 16-bit PCM;
6. each PCM frame is quantized to a 12-bit logical duty, scaled to the current
   PWM wrap, and duplicated twice;
7. the PWM wrap IRQ writes both compare levels together.

The six 1024-frame buffers still provide about 279 ms of decoded-audio
headroom. A 22050 Hz 16-bit stereo second requires about 22 sequential 4 KiB
reads instead of about 22050 frame-sized `fread()` calls.

## Underrun and lifecycle behavior

If a source is active and no ready buffer follows the playing buffer, the
underrun counter increments once for that episode. The wrap handler writes
centre duty until the producer recovers. After the final queued buffer drains,
the slice interrupt is disabled while PWM may retain centre duty without CPU
cost.

Explicit stop and STANDBY disable PWM and its slice interrupt, switch GP26 and
GP27 to SIO, and drive both pins LOW. The next BEEP, PLAY, WAV, or key click
restores PWM lazily.
A CPU-clock change stops active playback, recalculates the wrap, and leaves the
output in the same electrically quiet state.

## Output-headroom diagnostics

The wrap-IRQ build remained audibly unchanged on the real PicoCalc. The same
WAV is clean but substantially quieter under PicoMite, so these builds change
only one variable: the final common output amplitude.

The first diagnostic multiplied every signed PCM sample by 25 percent
immediately before the 12-bit logical PWM conversion. On real hardware,
headphone playback recovered some of the original sound, but remained far from
clean. That level-dependent improvement makes excessive modulation or analogue
overload the leading hypothesis, without yet proving it is the only cause.

The second diagnostic therefore uses exactly one eighth, or 12.5 percent, at
the same common boundary. This is after WAV volume, synthesis, and key-click
mixing, so the calibration applies equally to WAV, BEEP, PLAY, key click, and
`@SINE440`. PWM timing, IRQ pacing, buffering, parsing, resampling, and GPIO
configuration remain unchanged.

A full-scale WAV at the default 70 percent WAV Volume reaches at most 8.75
percent of signed full scale after the PicoCalc output calibration. This is deliberately conservative and is not yet the final
user-facing volume policy. A further clear improvement would strongly support
insufficient analogue headroom; no further improvement would indicate that a
second fault remains.

## Independent source-volume contract

Control Center now exposes two distinct settings:

- `BEEP/PLAY`: the existing `audio_volume` setting, including OFF and
  10-percent steps through 100 percent;
- `WAV Volume`: a new `wav_volume` setting with 10, 20, ... 100 percent.

WAV Volume applies only to decoded WAV samples and the `@SINE440` diagnostic.
It does not change BEEP, PLAY, or key click. BEEP/PLAY volume applies only to
the synthesizer. Key Click keeps its independent OFF/LOW/MID/HIGH source level.

`BEEP/PLAY` retains its 70-percent default. `WAV Volume` defaults to 50 percent,
which preserves the verified 12.5-percent WAV operating point. The new key is
persisted in `RMBASIC.CFG`; existing `audio_volume` remains backward compatible.
Existing development configurations that already contain `wav_volume=70` can
be changed to 50 percent from Control Center.

The output ceiling is now source-specific after mixing: BEEP, PLAY, and key
click retain 12.5 percent, while WAV and `@SINE440` may use up to 25 percent.
A key click mixed into a WAV buffer is compensated by 50 percent before the
higher WAV ceiling, so its physical level does not double.

For WAV, the menu maps 10, 20, ... 100 percent to 2.5, 5.0, ... 25.0 percent
of signed PCM full scale. Therefore WAV Volume 50 percent equals the verified
12.5-percent point and WAV Volume 100 percent is the deliberate upper limit.

## Remaining uncertainty and validation

The following are confirmed by source analysis and host tests:

- WAV format/decode for the supported combinations;
- 11025/22050/44100 phase stepping;
- sequential read-ahead behavior;
- FIFO ordering and underrun state;
- signed PCM to packed PWM scaling;
- exact two-period hold;
- clock-profile PWM timing.

Build 460 was tested on the real PicoCalc and produced the same distortion.
Together with the 22.05 kHz, 250 kHz, and 352.8 kHz hardware results, this
rejects carrier frequency and CPU-clock selection as the primary cause.
Clean playback by PicoMite on the same unit now isolates the remaining
difference to CPB's output backend, pad state, or effective analogue drive.
The wrap-IRQ backend is the direct test of that remaining boundary.

A temporary engineering source is therefore available through:

```basic
WAVPLAY "@SINE440"
```

It generates five one-second 440 Hz sine sections directly in signed PCM:
low-level stereo, medium-level stereo, high-level stereo, medium left-only,
and medium right-only, with quarter-second gaps. It bypasses the SD card,
RIFF parser, PCM decoder, resampler, WAV volume/tail path, and synth engine.
It retains only the common PCM-to-PWM conversion, IRQ transport, GPIOs, and
PicoCalc analogue path.

Interpretation:

- clean diagnostic sine: corruption remains in the WAV decode/render path;
- equally distorted diagnostic sine: the fault is in PCM-to-PWM conversion,
  GPIO/electrical output, board analogue circuitry, or the acoustic path;
- distortion that grows strongly with level: analogue clipping/nonlinearity;
- different left/right result: channel-specific hardware or routing fault.

An electrical or line-input capture of the headphone output remains the best
way to separate digital GPIO output from amplifier/speaker acoustics.
