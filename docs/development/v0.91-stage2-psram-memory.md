# Version 0.91 Stage 2 — PSRAM and SRAM Architecture

## Purpose

Stage 2 turns PicoCalc PSRAM from an editor-history-only resource into a shared
second memory tier, while reclaiming internal RP2350 SRAM without moving
latency-sensitive VM instructions, audio PWM buffers, UART/USB transport
buffers, keyboard state, or wireless state into PSRAM.

The implementation is deliberately conservative:

- PSRAM clients receive fixed non-overlapping regions.
- SD caching is read-only.
- ProgramStore retains an SRAM fallback.
- VM numeric and string arrays remain internal-SRAM runtime data, but are
  allocated only when DIM is executed.
- PSRAM diagnostics remain destructive and exclusive.

## PSRAM multi-client allocator

The former single-owner reservation is replaced with a fixed region allocator.
The allocatable clients are:

- Editor History
- Program Store
- SD Cache
- Direct State (reserved for future use)
- Audio Cache (reserved for future use)

Diagnostic use remains exclusive and is not a normal client allocation. The
final 16 bytes of the detected PSRAM remain reserved for the reversible hardware
probe and are never handed to clients.

Allocations are 16-byte aligned. A client can own at most one live region;
duplicate claims fail rather than aliasing the same address range.

System Information reports aggregate PSRAM usage and the principal client
allocations.

## INTERNAL RAM ProgramStore

The logical `INTERNAL RAM` Program Storage mode keeps its existing public
semantics and limits:

- 256 BASIC lines
- 191 body characters per line
- no SD dependency

On PicoCalc, its approximately 49 KiB `RamProgramStore` backing array now
prefers PSRAM. One `ProgramLine` scratch record remains in internal SRAM so the
existing borrowed-line API can be preserved.

If PSRAM is absent, unavailable, or cannot be claimed, ProgramStore falls back
to the previous internal-SRAM heap backend. Failure of PSRAM therefore does not
make BASIC editing unavailable.

Temporary ProgramStore instances cannot alias the active ProgramStore's PSRAM
region. They use SRAM fallback and may migrate to PSRAM after the previous owner
has released it.

## SD source read cache

SD-backed ProgramStore adds a bounded 64 KiB read-only PSRAM cache.

Policy:

- 2,048-byte PSRAM slots
- normally 32 cached BASIC line bodies
- SRAM contains metadata only
- lookup validates line index, body length and hash
- a PSRAM hit is copied into the existing SD scratch buffer
- one-open `visit_line_range()` remains the primary sequential viewport path
- range reads populate the cache for later random/single-line access
- no write-back and no dirty data are stored in the cache

The cache is invalidated or released when the underlying source identity can
change, including ProgramStore publication/recovery, USB MSC ownership
transitions, and relevant mode changes. This preserves the existing
transactional save and Storage Continuity model.

System Information exposes cache allocation and hit/miss counters.

The cache is disposable. Entering PSRAM reprobe or destructive diagnostics
releases the SD cache first. A live PSRAM-backed INTERNAL RAM ProgramStore still
correctly prevents destructive diagnostics because its source is not disposable.

## VM array SRAM reduction

Before Stage 2, every `VM` permanently contained:

- numeric array pool: 4,096 float cells = 16 KiB
- string array pool: 512 × 128 bytes = 64 KiB

These 80 KiB were reserved even when a BASIC program never executed `DIM`.

Stage 2 removes the fixed pools from `VM`. `run_impl()` now:

1. starts without array backing storage;
2. allocates the numeric pool on the first numeric `DIM`;
3. allocates the string pool on the first string `DIM`;
4. keeps the pools in internal SRAM for normal VM-speed access;
5. releases them automatically on every return from RUN/direct execution.

Array capacities and BASIC-visible errors remain unchanged. This is a lifetime
optimization, not a PSRAM migration, so normal array access does not inherit
PIO-PSRAM latency.

## Host and CI validation

The Stage 2 regression suite covers:

- multi-client PSRAM allocation, reuse, exhaustion and duplicate-claim refusal;
- PSRAM-backed INTERNAL RAM ProgramStore;
- ProgramStore transactional save/fault injection;
- SD cache allocation and repeat-read hit behavior;
- Storage Continuity/session recovery;
- VM RUN/direct execution under ASan/UBSan, including existing array coverage;
- Editor/Undo/Redo, Bluetooth HID, USB MSC, audio, network and existing
  regression suites;
- normal Pico 2 W firmware build;
- editor-performance firmware build;
- memory and compiler stack reports.

The static SRAM reduction comes primarily from removing the persistent 80 KiB
VM array pools. ProgramStore PSRAM additionally saves about 49 KiB of runtime
heap whenever the logical INTERNAL RAM backend can use PSRAM; that runtime
saving is not part of the linker .data/.bss figures above.

The VM array capacity has not been reduced: 16 KiB numeric and 64 KiB string
array pools are still available on demand.
